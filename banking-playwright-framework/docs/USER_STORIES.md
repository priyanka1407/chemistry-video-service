# User stories → acceptance criteria → boundary values

BVA takes each acceptance criterion that defines a **range**, **length**, **date window** or **threshold** and tests *just below / on / just above* every edge (ε = the smallest meaningful step), plus one nominal value per equivalence partition. Test cases are generated by `BoundaryValues` so the table and the code can't disagree.

## PAY-101 Initiate a domestic payment (role MAKER)

> *As a maker, I want to pay a saved beneficiary from a company account, so that suppliers are paid on time.*

| AC | Rule | ε | Boundary cases → expected | Test |
|---|---|---|---|---|
| AC1 | 0.01 ≤ amount ≤ 50,000.00, max 2 dp | 0.01 | 0.00 ✗ · **0.01 ✓** · 0.02 ✓ · 25,000.00 ✓ · 49,999.99 ✓ · **50,000.00 ✓** · 50,000.01 ✗ | `amount_range_boundaries` |
| AC1 | format (equivalence classes) | — | `abc` · `10.001` · `-5.00` · `1e3` · `1,000.00` (API) · blank · `0` → all ✗ | `amount_invalid_equivalence_classes` |
| AC2 | amount > 10,000.00 → needs checker approval | 0.01 | 9,999.99 → auto · **10,000.00 → auto** · 10,000.01 → approval | `approval_threshold_boundaries` |
| AC3 | reference required, 1–18 chars | 1 char | 0 ✗ · **1 ✓** · 2 ✓ · 17 ✓ · **18 ✓** · 19 ✗ | `reference_length_boundaries`, `ui_reference_max_length` |
| AC4 | today ≤ payment date ≤ today + 30 (Europe/London) | 1 day | -1 ✗ · **0 ✓** · 1 ✓ · 29 ✓ · **30 ✓** · 31 ✗ | `execution_date_boundaries` |

The UI layer re-tests only the outermost failures (0.00, 50,000.01, 3 dp, 19 chars), to prove each message is bound to the right field and exposed accessibly (`aria-invalid`). The full matrix runs through the API, where each case takes milliseconds.
